# Conversion Deduplication

## 1. Overview
This document explains the deduplication architecture for MsingiPACK. Its core purpose is to ensure that one real-world financial conversion does not become multiple analytics or advertising conversions due to browser behavior.

## 2. Original Duplication Problem
Historically, MsingiPACK suffered from severe conversion inflation. The original project baseline identified a critical anomaly:
**33 purchase events tracked from only 4 unique buyers.**

One customer interacting normally with the site was artificially inflating revenue metrics, poisoning marketing ROI and analytics accuracy.

## 3. Why Duplicate Conversions Occurred
The mechanism for this failure was tied to the browser event lifecycle, which was not inherently equivalent to the financial transaction lifecycle. 

The flow was:
Payment succeeds ➔ Receipt page loads ➔ Purchase tag fires ➔ **User refreshes page / restores tab** ➔ Purchase tag fires again.

Because the trigger was tied to the *page load* rather than the *transaction state*, every refresh generated a new analytics purchase.

## 4. Deduplication Strategy
To resolve this, we implemented two separate but complementary layers of protection:
1.  **Transaction Identity:** "Is this the same transaction?" (Platform-level deduplication).
2.  **Retrigger Protection:** "Should this page load fire the event again?" (Client-level deduplication).

## 5. Transaction Identity
We shifted from relying on timestamps, session IDs, or page URLs to utilizing the **M-PESA receipt number**. 

M-PESA receipt number ➔ `transaction_id` ➔ Unique business transaction.

Because this string (e.g., `NL810XX99`) is generated by the financial source of truth, it is completely stable regardless of how many times a browser refreshes.

## 6. GA4 Deduplication
Google Analytics 4 uses the `transaction_id` parameter natively to prevent duplicate ecommerce transactions. 
If GA4 receives multiple `purchase` events with the exact same `transaction_id`, it processes the first one and discards subsequent identical IDs. 

## 7. Meta Deduplication
Meta relies on a unique parameter to deduplicate conversion signals:
`transaction_id` ➔ Meta `eventID` ➔ Meta Deduplication.

By explicitly mapping the M-PESA receipt number to Meta's `eventID` parameter, the Meta Pixel understands that 5 signals with the same `eventID` represent a single purchase. This ensures ad campaigns are not artificially credited with duplicate ROAS (Return on Ad Spend).

## 8. Receipt / Page Refresh Protection
Relying solely on backend platform deduplication is inefficient and risks data leaks. We also implemented Retrigger Protection driven by the backend.

**The Fix:**
The Moodle backend is configured to inject the `mpesa_purchase_success` `dataLayer` push *only on the initial successful redirect/render* following the M-PESA callback. If the user hits "Refresh" on the receipt page, the backend recognizes the transaction as already acknowledged and renders the page *without* the `dataLayer` event.

*   **Transaction identity** handles backend platform deduplication (if the event somehow fires twice).
*   **Retrigger protection** stops the browser from firing the script twice in the first place.

## 9. Failure / Edge Cases
*   **Missing Receipt Code:** If M-PESA fails to return a receipt number, the `mpesa_purchase_success` event is **blocked entirely**. We do not generate synthetic or fake transaction IDs. A synthetic identifier prevents technical duplication but destroys the ability to reconcile the event to the financial ledger. 
*   **Null IDs:** A null `transaction_id` breaks deduplication across all platforms. Blocking the event preserves financial data integrity.

## 10. Validation
To validate the deduplication architecture:
1.  Process 1 real payment.
2.  Verify 1 valid GA4 and Meta purchase is fired.
3.  **Refresh the receipt page 5 times.**
4.  Verify no additional `mpesa_purchase_success` events appear in the `dataLayer` or network requests.
5.  Wait 24 hours and verify GA4 and Meta only report 1 transaction.

## 11. Reconciliation
By matching total unique `transaction_id`s in GA4 against total rows in the Moodle database for a given date range, we can calculate tracking loss without the noise of duplicate events skewing the math.

## 12. Limitations
Deduplication relies on exactly matching strings. If a tracking parameter alters the capitalization or strips characters from the `transaction_id` before dispatching to Meta/GA4, the platforms will treat it as a new transaction and fail to deduplicate.
