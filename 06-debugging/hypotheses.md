# Debugging Hypotheses

## 1. Overview
This document translates the business symptoms observed in the MsingiPACK platform into testable engineering hypotheses.

## 2. Hypothesis Method
Each entry defines the observation, the mechanical assumption, expected behavior, failure signature, required evidence, the test performed, and the conclusive result.

## 3. H1 — Landing / Redirect Attribution Failure

### Observation
Paid traffic landing on `academy.msingipack.com` course pages shows a near 100% bounce rate. Conversions are heavily skewed toward "Direct".

### Hypothesis
Moodle's `require_login()` function intercepts unauthenticated traffic and redirects users to the login page, dropping all URL query parameters (like `utm_source`) in the 302 redirect.

### Expected Behavior
A visitor clicking an ad should have tracking parameters preserved in the URL or stored in a session cookie prior to any redirect.

### Expected Failure Signature
The network tab will show an initial request with parameters, followed by a redirect to `academy.msingipack.com/login/index.php` with a clean URL. 

### Evidence Required
Network request logs showing the drop of query parameters between the requested URL and the resolved URL.

### Test
Open a private browser window. Navigate to `https://academy.msingipack.com/course/view.php?id=2&utm_source=test`. Observe network requests.

### Result
Initial request returned 302. Redirected to `/login/index.php`. UTM parameters were missing from the final resolved URL.

### Conclusion
**Supported.**

## 4. H2 — Registration Measurement Misalignment

### Observation
Analytics platforms report more registrations than the actual number of Moodle accounts created.

### Hypothesis
The tracking setup conflates intent with action. The GTM tag is firing on a front-end CTA click rather than relying on Moodle as the source of truth for a confirmed account creation.

### Expected Behavior
A registration event should only fire upon a confirmed database entry or explicit post-registration success state generated by Moodle.

### Expected Failure Signature
Triggering form validation errors (e.g., submitting an existing email address) will fire the registration conversion event.

### Evidence Required
GTM preview mode firing the registration tag despite a failed form submission.

### Test
Fill out the MsingiPACK registration form with an already registered email. Click the submission CTA.

### Result
GTM fired the registration tag based on the click trigger. The server returned a UI error. No new Moodle account was created.

### Conclusion
**Supported.**

## 5. H3 — Post-Registration Activation Failure

### Observation
Activation (first login) is not being reliably tied back to the original acquisition source.

### Hypothesis
Because registration and activation are distinct steps separated by time and state changes, the lack of persistent tracking parameters during the Moodle account creation process orphans the subsequent activation event.

### Expected Behavior
User registers, lands on success page, and triggers activation. The original session ID should bridge the gap.

### Expected Failure Signature
The user journey stops at registration. The subsequent login happens in a new session.

### Evidence Required
Funnel exploration in GA4 showing a hard drop-off between registration and activation.

### Test
Complete registration workflow. Observe GA4 Realtime for session continuation upon first login.

### Result
Original session ended post-registration. Activation triggered a new session without attribution back to the acquisition source.

### Conclusion
**Supported.**

## 6. H4 — Purchase Attribution / Deduplication Failure

### Observation
Analytics revenue is inflated compared to actual database enrollment records.

### Hypothesis
Users navigating back to the course enrollment success page (via browser history or refresh) are re-triggering the data layer push, and GA4 is not deduplicating these events because a `transaction_id` is missing.

### Expected Behavior
A purchase event should fire once per completed payment. Subsequent page loads should pass a `transaction_id` for deduplication.

### Expected Failure Signature
Refreshing the enrollment success page pushes a new `purchase` event to the data layer with `transaction_id: undefined`.

### Evidence Required
GTM preview mode data layer payload inspection on page reload.

### Test
Complete a test enrollment. Land on the success page. Refresh the page. Observe the data layer.

### Result
`purchase` event fired on initial load. Fired again on reload. The payload lacked a unique transaction ID.

### Conclusion
**Supported.**
